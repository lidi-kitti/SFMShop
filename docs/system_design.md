# Системный дизайн проекта SFMShop

SFMShop — REST-магазин: каталог, пользователи, заказы. Источник истины — PostgreSQL; Redis ускоряет повторные чтения и держит сессии; MongoDB принимает логи. Веб-слой — FastAPI (`src/api/main.py`). Ниже — как система устроена, как растёт и какие компромиссы уже заложены в код.

Смежные документы: [db_architecture.md](db_architecture.md), [db_scaling_strategy.md](db_scaling_strategy.md), [database_selection.md](database_selection.md).

## Архитектура

### Компоненты:

- **API (FastAPI / uvicorn).** JSON-маршруты `/products`, `/orders`, `/users`, `/login`. Валидация Pydantic, сессия `Authorization: Bearer`, rate limit (slowapi).
- **Домен и сервисы.** Модели `User` / `Product` / `Order`, `CacheService`, фоновая обработка заказов (`BackgroundTasks`, `process_orders_async`).
- **PostgreSQL.** Таблицы `users`, `products`, `orders`, `order_items`. Запись — primary; чтение витрины и списков — replica (`get_session(read_only=True)`).
- **Redis.** Cache-aside каталога и пользователей; сессии `session:{uuid}`. Не источник заказов.
- **MongoDB.** Access/error логи API (`LogService`). Сбой логов не останавливает checkout.

```text
Клиент ──► FastAPI ──► Redis (кэш, сессия)
                 ├──► PostgreSQL primary  (запись заказа, остаток)
                 ├──► PostgreSQL replica  (витрина, история)
                 └──► MongoDB             (логи)
```

### Масштабирование:

Порядок тот же, что у БД: сначала вертикаль и индексы, потом чтение, потом запись.

| Слой | Как масштабировать | Когда |
|------|-------------------|--------|
| API | Несколько uvicorn-воркеров / инстансов за балансировщиком (stateless: сессия в Redis) | CPU event loop, рост RPS витрины |
| PostgreSQL | Read-replicas для `GET /products` и истории; шарды по `user_id` — только когда primary не держит запись `orders` | Реплика — чтения ≫ записи; шард — объём/write primary |
| Redis | Отдельный инстанс (или replica Redis) под кэш и сессии | Кэш должен разгружать SQL, а не жить в той же RAM, что приложение |
| MongoDB | Ротация и TTL-индекс логов; при росте потока — отдельный узел | Логи не должны делить диск с заказами |

Горизонталь API дешёвая, потому что состояние запроса не в процессе: каталог читается из Redis/replica, сессия — ключ в Redis. Заказ остаётся на primary: без этого легко получить оверселл.

### Кэширование:

Стратегия — **cache-aside** в `CacheService`: сначала Redis, при промахе — replica PostgreSQL, затем `SETEX`. После `COMMIT` на primary ключи сбрасываются (`invalidate_products`, `invalidate_product`), иначе витрина врёт дольше TTL.

| Ключ | Что | TTL | Заголовок клиенту |
|------|-----|-----|-------------------|
| `products:all`, `product:{id}` | Витрина и карточка | 1 час (`CacheService.TTL = 3600`) | `Cache-Control: public, max-age=3600` |
| `users:all`, `user:{id}` | Списки пользователей | 1 час | `private, no-store` |
| `session:{id}` | Кто залогинен | 24 часа (`SESSION_TTL = 86400`) | не кэшируется |

Не кэшируются: создание заказа, списание `stock`, ответ `POST`/`PUT`/`DELETE` (`no-store`). Остаток и сумма заказа всегда из PostgreSQL.

## Метрики производительности

Смотреть не «магазин в целом», а узкое место каждого слоя.

| Метрика | Зачем SFMShop | Ориентир |
|---------|---------------|----------|
| **Latency p50 / p99** `GET /products`, `GET /products/{id}` | Витрина должна быть быстрой; рост p99 — промах кэша или лаг replica | p50 с Redis — единицы–десятки мс; p99 без кэша упирается в SQL |
| **Latency p99** `POST /orders` | Checkout важнее среднего RPS: блокировка строки товара, транзакция | хуже витрины — это норма; деградация = lock / диск primary |
| **Cache hit ratio** `products:all` / `product:{id}` | Низкий hit → replica снова под SELECT каталога | цель — высокий hit между сменами цены/остатка |
| **Replication lag** | Сильный лаг → витрина и кэш наполняются устаревшим `stock` | read-your-writes после своего заказа — с primary |
| **RPS и ошибки 429 / 5xx** | Limiter режет всплески; 5xx — пул БД, Redis, таймауты | отдельно витрина и запись |
| **Размер ответа и время сервера** | `measure_api_performance` в `src/api/main.py`: DNS, total, `response.elapsed`, size | пагинация и gzip, если JSON каталога растёт |

Throughput витрины наращивают кэшем и репликами. Throughput оформления заказов упирается в primary — его не «лечат» Redis.

## Компромиссы

- **Модель согласованности для разных данных:**
  - Заказ, остаток, баланс — **строгая (ACID)** на primary: один `COMMIT` (заказ + позиции + `stock`).
  - Витрина — **ослабленная**: Redis и replica могут отставать до TTL или до лага WAL. Для карточки цены это приемлемо; для списания — нет.
  - Сессия — **volatile с TTL**: потеря Redis = повторный логин, заказ на месте.
  - Логи — **eventual / best-effort**: потеря одной записи хуже, чем останов checkout.

- **TTL кэша и обоснование:**
  - **1 час на каталог** — товар меняют редко относительно числа `GET`; час ограничивает окно «старая цена на витрине», если инвалидация не сработала. Короче TTL — больше нагрузка на replica; длиннее — дольше врать после смены цены.
  - **24 часа на сессию** — день работы без повторного логина; не строка в `users` на каждый запрос. Дольше — выше риск украденного Bearer; короче — лишние `POST /login`.
  - Инвалидация после `COMMIT` сужает окно рассинхрона; TTL — страховка, не замена сброса ключа.

- **Что важнее — latency или throughput:**
  - **Витрина — latency.** Покупатель ждёт карточку, не «миллион заказов в секунду». Redis + replica режут хвост задержки повторных GET.
  - **Checkout — корректность, затем latency одного запроса.** Важнее не потерять остаток и не оформить заказ без пользователя, чем максимизировать RPS `POST /orders`.
  - **Логи — throughput записи.** Append в MongoDB не должен тормозить ответ API; лаг лога допустим.
  - Итог: для SFMShop на горячем пути витрины важнее **низкая задержка чтения**; на пути денег — **согласованность**, даже ценой меньшего throughput записи.
