# Гибридная архитектура БД SFMShop

SFMShop — интернет-магазин: каталог, пользователи, заказы, сессии витрины, фоновые задачи (уведомления, оплата) и поток служебных событий (логи API, аналитика кликов, ошибки оплаты). Эти нагрузки **различаются по структуре, согласованности и паттерну доступа**. Одна СУБД на все роли либо усложняет модель, либо проигрывает по задержке и объёму.

Поэтому расширенный проект использует **polyglot persistence** (гибридную схему):

| Роль | СУБД | Что хранит |
|------|------|------------|
| Источник истины | **PostgreSQL** | Пользователи, товары, заказы, позиции заказов |
| Горячий слой | **Redis** | Кэш витрины, сессии, очереди задач |
| События и аналитика | **MongoDB** | Логи, аналитические события, произвольные документы |

Критерии выбора СУБД — в [database_selection.md](database_selection.md). Сравнение PostgreSQL и MongoDB как кандидатов на ядро магазина — в [postgresql_vs_mongodb_sfmshop_analysis.md](postgresql_vs_mongodb_sfmshop_analysis.md). Масштабирование PostgreSQL (реплики, шарды) — в [db_scaling_strategy.md](db_scaling_strategy.md).

Этот документ фиксирует **как три хранилища стыкуются в одну систему**: карту данных, обоснование ролей, схему архитектуры и поток сценария.

## 1. Схема архитектуры

```text
                         ┌─────────────────────┐
                         │   Клиент / API      │
                         │   (FastAPI, витрина)│
                         └──────────┬──────────┘
                                    │
                         ┌──────────▼──────────┐
                         │   Приложение        │
                         │   SFMShop           │
                         │   queries.py        │
                         │   cache_service.py  │
                         │   log_service.py    │
                         └──┬────────┬──────┬──┘
              запись/чтение │        │      │  append событий
              ACID, JOIN    │        │      │
                            │        │      │
         ┌──────────────────▼─┐  ┌───▼────┐ │  ┌──────────────────┐
         │   PostgreSQL       │  │ Redis  │ │  │   MongoDB        │
         │   source of truth  │  │        │ │  │   sfmshop_logs   │
         │                    │  │ кэш    │ │  │                  │
         │  users             │  │ сессии │ │  │  logs            │
         │  products          │  │ очереди│ │  │  events          │
         │  orders            │  │        │ │  │  analytics       │
         │  order_items       │  └───┬────┘ │  └────────▲─────────┘
         │                    │      │      │           │
         │  primary ──WAL──►  │      │      │           │
         │  replica (чтение)  │      │      └───────────┘
         └────────────────────┘      │
                                     │ worker читает очередь
                                     ▼
                              ┌──────────────┐
                              │  Workers     │
                              │  (email,     │
                              │   оплата,    │
                              │   аналитика) │
                              └──────────────┘
```

Правило границ: **PostgreSQL отвечает на «что правда»; Redis — на «что быстро отдать сейчас»; MongoDB — на «что произошло».** Сбой Redis не уничтожает заказ. Сбой MongoDB не останавливает checkout. Сбой PostgreSQL останавливает магазин — там источник истины.

## 2. Карта данных: что где лежит

### 2.1. PostgreSQL — пользователи, товары, заказы

Источник истины. Схема уже есть в `src/database/models.py` и `src/database/create_sfmshop_db.sql`.

| Сущность | Таблица | Почему здесь |
|----------|---------|--------------|
| Пользователь | `users` | Уникальный `email`, FK от заказов, долгоживущая запись |
| Товар | `products` | Цена `Numeric(10, 2)`, остаток `quantity`, каталог общий для всех |
| Заказ | `orders` | FK на `users.id`, сумма, транзакция вместе с позициями и остатком |
| Позиция заказа | `order_items` | FK на `orders.id` и `products.id`; цена на момент покупки |

Запись — на primary (`DB_PRIMARY_HOST`). Чтение витрины и истории — с replica (`get_session(read_only=True)`).

**Не кладём сюда:** сессии (TTL, высокая частота записи), сырые логи API, клики витрины. Они раздувают бэкапы ядра и конкурируют с `create_order` за I/O.

### 2.2. Redis — кэш, сессии, очереди

Не источник истины. Данные либо восстанавливаются из PostgreSQL, либо истекают по TTL, либо живут только пока задача не обработана.

| Назначение | Ключ / структура | TTL | Почему здесь |
|------------|------------------|-----|--------------|
| Кэш каталога | `products:all` | 1 час | Список витрины читают чаще, чем меняют |
| Кэш карточки | `product:{id}` | 1 час | Точечный GET без SQL |
| Сессия | `session:{uuid}` | 24 часа | Кто залогинен, без строки в `users` на каждый запрос |
| Очередь писем | `queue:email` (List / Stream) | до обработки | Письмо «заказ создан» не должно держать HTTP-запрос |
| Очередь оплаты | `queue:payment` | до обработки | Повтор и отложенная обработка платежа |
| Очередь аналитики | `queue:analytics` | до обработки | Буфер перед записью события в MongoDB |

В коде уже есть кэш и сессии (`src/services/cache_service.py`: `get_cached_products`, `create_user_session`, `invalidate_product_cache`). Очереди — слой расширенного проекта: worker забирает задачу, выполняет её, при ошибке возвращает в очередь или пишет dead-letter.

**Не кладём сюда:** заказы и остатки. Persistence Redis слабее WAL PostgreSQL; eviction и TTL противоречат «заказ живёт годы».

### 2.3. MongoDB — логи, аналитика, события

Документное хранилище без FK на заказы. База `sfmshop_logs`, коллекции ниже. Запись — `insert_one` / `insert_many`, без транзакции с PostgreSQL.

| Коллекция | Что внутри | Почему здесь |
|-----------|------------|--------------|
| `logs` | Access/error логи API: `type`, `endpoint`, `status_code`, `ip`, `message`, произвольные поля | Уже в `src/services/log_service.py` |
| `events` | Доменные события: `order_created`, `payment_failed`, `cart_abandoned`; разный набор полей у каждого типа | Гибкая схема, append-only, JOIN с заказами не нужен |
| `analytics` | Клики, просмотры карточек, воронка: `user_id` (если есть), `product_id`, `action`, `payload` | Высокий поток вставок, фильтры и `$group`, схема эволюционирует |

Потеря одной записи лога или клика хуже, чем рассинхрон заказа, но **не ломает оформление**. Завтра в документ можно добавить `user_agent` или `request_id` без миграции всех исторических строк.

**Не кладём сюда:** пользователей, каталог и заказы. Нет классических FK; целостность и отчёты «заказ + позиции + пользователь» уезжают в приложение.

## 3. Обоснование выбора каждой СУБД

Выбор — не «популярность движка», а соответствие модели данных и гарантий нагрузке.

### 3.1. Почему PostgreSQL для users / products / orders

- **Связи.** Один пользователь — много заказов; заказ — много позиций; позиция ссылается на товар. В схеме это `ForeignKey('users.id')`, `ForeignKey('orders.id')`, `ForeignKey('products.id')`. SQL JOIN собирает «заказ + товары + пользователь» без денормализации каталога в каждый заказ (`get_user_order_history`, `get_orders_with_products`).
- **Целостность ACID.** Уникальный `email`, денежный `Numeric(10, 2)`, `CHECK (quantity >= 0)`. Один `COMMIT`: заказ + позиции + списание остатка. БД отклоняет заказ с несуществующим `user_id`. Остаток нельзя решать «примерно».
- **Стабильная схема.** Поля заказа и товара меняются редко; миграции DDL версионируют контракт.
- **Долговечность.** Заказ и оплата должны пережить рестарт приложения, `FLUSHALL` в Redis и сбой MongoDB.

Почему не MongoDB и не Redis на эту роль — см. таблицу в §6 `database_selection.md`. Кратко: MongoDB не даёт классических FK; Redis — RAM, нет JOIN и денежных ограничений.

### 3.2. Почему Redis для кэша / сессий / очередей

- **Ключ–значение и O(1).** `GET products:all`, `GET session:{uuid}` — точечное чтение без JOIN. Обращение по ключу в RAM дешевле SQL по `products` на каждый `GET /products`.
- **TTL как штатный механизм.** Сессия истекает за 24 часа (`setex(..., 86400, ...)`), кэш товара — за час. Не нужна отдельная джоба «почистить просроченные строки».
- **Ослабление согласованности допустимо.** Витрина может отставать до TTL или до `invalidate_products_cache()`. Для карточки это приемлемо; для списания остатка — нет (остаток читается из PostgreSQL).
- **Очереди.** List (`LPUSH`/`BRPOP`) или Stream (`XADD`/`XREADGROUP`) закрывают «сделай потом»: письмо, ретрай оплаты, слив клика в MongoDB. HTTP-запрос checkout не ждёт SMTP. Задача в очереди эфемерна — после успеха её можно удалить.

Почему не PostgreSQL: кэш в той же БД, что заказы, не разгружает primary и не даёт естественного TTL. Почему не MongoDB: выше латентность, чем у in-memory KV; нет `SETEX` как основного API; для очереди это лишняя постоянная коллекция.

### 3.3. Почему MongoDB для логов / аналитики / событий

- **Гибкая схема.** У access-лога есть `endpoint` и `status_code`, у error — `message` и `stack`, у клика — `product_id` и `referrer`. `save_log` принимает словарь. Не нужно заранее описывать все колонки.
- **Append-only и объём.** Поток вставок велик относительно изменения схемы. Документная модель и TTL-индекс по `timestamp` здесь естественнее, чем бесконечно растущая таблица рядом с `orders`.
- **Запросы без JOIN с ядром.** `get_logs_by_type`, `get_logs_by_status_code` (`$gte`/`$lt`), агрегация `$group` по `type` и `status_code`. Это поиск по документам, а не «заказ + позиции + пользователь».
- **Слабая связь с деньгами.** Задержка или потеря одного события аналитики не откатывает заказ. Событие можно писать асинхронно (через Redis-очередь), не держа транзакцию PostgreSQL.

Почему не PostgreSQL: жёсткая схема или «простыня» JSONB; рост таблицы конкурирует с `VACUUM` и бэкапами заказов; ядро и «свалка событий» делят один контур восстановления. Почему не Redis: RAM и eviction конфликтуют с «найти ошибки за неделю» и воронкой за месяц.

## 4. Поток данных: создание заказа

Сценарий `POST /orders`: пользователь оформляет заказ с позиции витрины. Цель — показать, как три БД участвуют в одном запросе, не подменяя друг друга.

```text
Клиент
  │  POST /orders  {user_id, items}
  ▼
Приложение
  │
  │  1. Проверка сессии
  │     Redis GET session:{id}  →  {user_id}
  │     (промах → 401, заказ не создаём)
  │
  │  2. Запись истины — одна транзакция PostgreSQL (primary)
  │     BEGIN
  │       INSERT INTO orders (...)
  │       INSERT INTO order_items (...)
  │       UPDATE products SET quantity = quantity - n  WHERE id = ...
  │     COMMIT  →  order_id
  │
  │  3. Инвалидация кэша витрины
  │     Redis DEL products:all
  │     Redis DEL product:{id}   для каждого купленного товара
  │     (иначе витрина врёт по остатку до истечения TTL)
  │
  │  4. Постановка фоновых задач
  │     Redis LPUSH queue:email     {type: order_created, order_id, email}
  │     Redis LPUSH queue:payment   {order_id, amount}   — если оплата не синхронная
  │
  │  5. Событие и лог (не в той же транзакции, что заказ)
  │     MongoDB insert logs     {type: "access", endpoint: "/orders", status_code: 201}
  │     MongoDB insert events   {type: "order_created", order_id, user_id, total}
  │
  ▼
Ответ клиенту: 201 {order_id}
```

Что из этого уже есть в коде, а что — слой расширенного проекта:

| Шаг | Сейчас | Расширение |
|-----|--------|------------|
| 1. Сессия | `get_user_session` в `cache_service.py` | Тот же ключ `session:{uuid}` |
| 2. Запись заказа | `create_order` в `queries.py` на primary | Транзакция вместе с `order_items` и остатком |
| 3. Инвалидация | `invalidate_products_cache`, `invalidate_product_cache` | Вызывать сразу после COMMIT |
| 4. Очереди | нет | Redis List/Stream + worker |
| 5. Лог / событие | `save_log` в `log_service.py` | Плюс коллекция `events` |

### Гарантии и порядок

1. **Сначала PostgreSQL.** Если `COMMIT` не прошёл (нет товара, FK, ошибка связи) — Redis и MongoDB не трогаем. Клиент получает ошибку, «фантомного» заказа нет.
2. **Инвалидация Redis после COMMIT.** Кэш — производное от PostgreSQL. Удалить ключ до записи опасно: параллельный `GET /products` успеет положить в Redis старый остаток. Удалить после — штатно: следующий запрос витрины пойдёт в PostgreSQL (`get_cached_products`: cache-aside).
3. **MongoDB и очереди — best effort относительно заказа.** Если `insert_one` в MongoDB упал, заказ уже существует. Лог можно дописать позже или потерять одну запись. Если `LPUSH` в очередь писем упал — заказ валиден, письмо не уйдёт; это операционная проблема, не целостность денег.
4. **Worker очереди** читает `queue:email`, отправляет письмо, пишет в MongoDB `events` факт `email_sent` (или `email_failed`). PostgreSQL при этом не обновляется, если статус письма не часть домена заказа.

### Чтение после создания (read-your-writes)

Следующий `GET` этого заказа идёт на **primary**, не на replica и не в Redis: реплика может отстать, кэша заказа нет (и не должно быть как источника истины). Каталог для остальных пользователей по-прежнему читается из Redis / replica.

## 5. Поток данных: просмотр витрины (для контраста)

Чтение каталога не пишет в PostgreSQL и почти не трогает MongoDB.

```text
GET /products
  → Redis GET products:all
       попадание → отдать JSON, лог access в MongoDB (опционально)
       промах    → PostgreSQL replica: get_all_products()
                 → Redis SETEX products:all 3600
                 → отдать JSON
```

Сессия проверяется в Redis. Аналитика просмотра (`product_viewed`) уходит в MongoDB `analytics` — либо сразу, либо через `queue:analytics`, чтобы не замедлять витрину.

## 6. Минусы гибридной схемы

Три СУБД дают каждой нагрузке подходящий движок. Цена — не в выборе PostgreSQL или Redis по отдельности, а в том, что они работают **вместе**.

### 6.1. Сложность

- Три клиента в приложении (`psycopg2`/`SQLAlchemy`, `redis-py`, `pymongo`), три набора DSN, три модели ошибок и таймаутов.
- Нужно явно знать, куда писать: заказ — только PostgreSQL, сессия — только Redis, лог — только MongoDB. Ошибка «положили заказ в Redis» не ловится схемой.
- Локальная разработка, CI и staging поднимают не один контейнер, а связку PostgreSQL + replica + Redis + MongoDB.
- Наблюдаемость: три набора метрик (лаг реплики, eviction Redis, размер коллекций MongoDB), три дашборда, три алерта «диск кончился».

### 6.2. Синхронизация и согласованность между хранилищами

Между БД **нет общей транзакции**. Отсюда дыры:

| Ситуация | Что происходит |
|----------|----------------|
| COMMIT в PostgreSQL прошёл, `DEL products:all` не прошёл | Витрина показывает старый остаток до TTL (до часа) |
| COMMIT прошёл, `save_log` / `events` не записались | Заказ есть, в аналитике его нет; воронка врёт |
| `LPUSH queue:email` не прошёл | Покупатель не получит письмо, заказ валиден |
| Worker обработал очередь, MongoDB недоступна | Письмо ушло, события `email_sent` нет |
| Реплика PostgreSQL отстаёт, кэш уже инвалидирован | `get_cached_products` читает replica и кладёт в Redis ещё не обновлённый каталог |

Смягчение — идемпотентные воркеры, повтор инвалидации, outbox в PostgreSQL («событие к отправке» как строка в той же транзакции, что заказ), мониторинг рассинхрона. Это дополнительный код, которого нет при одной БД.

### 6.3. Больше компонентов для поддержки

| Компонент | Что сопровождать |
|-----------|------------------|
| PostgreSQL primary + replica | Бэкапы WAL, failover, миграции схемы, права, `VACUUM` |
| Redis | Память, eviction, persistence (AOF/RDB) если сессии жалко терять, мониторинг ключей без TTL |
| MongoDB | Репликасет, TTL-индексы на логи, ротация, место под `analytics` |
| Workers очередей | Деплой, ретраи, dead-letter, идемпотентность |
| Сеть и секреты | Три контура доступа, три поверхности атаки |

Отказ любого компонента даёт **разный** эффект: Redis — просела витрина и слетели сессии; MongoDB — нет логов и аналитики, магазин жив; PostgreSQL — магазин стоит. Операционная модель сложнее, чем «упала одна БД — чиним одну БД».

Плюс стоимость: лицензии/инстансы, обучение команды трём движкам, разные тулы бэкапа и восстановления.

## 7. Сводка

```text
                    SFMShop
                       │
     ┌─────────────────┼─────────────────┐
     ▼                 ▼                 ▼
PostgreSQL           Redis            MongoDB
users                products:all     logs
products             product:{id}     events
orders               session:{uuid}   analytics
order_items          queue:*
     │                 │                 │
  ACID, FK, JOIN    TTL, O(1), очередь  документ, append
  деньги и связи    скорость и буфер    «что произошло»
```

| Вопрос | Ответ для SFMShop |
|--------|-------------------|
| Где правда о заказе? | PostgreSQL, и только там |
| Откуда витрина берёт список товаров? | Redis; при промахе — replica PostgreSQL |
| Кто пользователь в этом запросе? | Redis `session:*` |
| Куда уходит письмо и ретрай оплаты? | Redis-очередь, worker |
| Где логи API и воронка? | MongoDB `logs` / `events` / `analytics` |

Гибрид оправдан тем, что критерии нагрузок расходятся: ядро требует ACID и JOIN, витрина — миллисекундный ключ с TTL, события — гибкую схему и поток вставок. Минусы (сложность, рассинхрон, три контура поддержки) — плата за то, что ни одна СУБД не выполняет чужую роль.
