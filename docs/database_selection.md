# Выбор СУБД для SFMShop

SFMShop — интернет-магазин: каталог, пользователи, заказы, сессии витрины и поток служебных событий (логи API, ошибки оплаты). Эти нагрузки **различаются по структуре, согласованности и паттерну доступа**. Одна СУБД на все роли либо усложняет модель, либо проигрывает по задержке и объёму. Поэтому проект использует **polyglot persistence**: PostgreSQL — источник истины, Redis — кэш и сессии, MongoDB — логи.

Документ фиксирует **критерии выбора** и применяет их к сущностям SFMShop. Сравнение PostgreSQL и MongoDB именно как кандидатов на *ядро* магазина — в [postgresql_vs_mongodb_sfmshop_analysis.md](postgresql_vs_mongodb_sfmshop_analysis.md).

---

## 1. Критерии выбора хранилища

Перед выбором движка оценивают не «популярность СУБД», а свойства данных и запросов.

| Критерий | Вопрос | Почему важен |
|----------|--------|--------------|
| **Структура** | Есть ли стабильные связи и инварианты (FK, уникальность, суммы)? Или документы с разным набором полей? Или пары ключ–значение с TTL? | Реляционная схема, документ и KV-кэш закрывают разные модели |
| **Согласованность** | Нужен ли один `COMMIT` (заказ + позиции + остаток)? Допустима ли устаревшая копия на секунды? Данные можно потерять при рестарте? | ACID vs eventual consistency vs volatile cache |
| **Запросы** | JOIN и агрегаты? Точечное `GET` по ключу? Фильтр по произвольным полям без жёсткой схемы? | Оптимизатор SQL, O(1) по ключу, индекс по полям документа |
| **Нагрузка** | Много чтений одного и того же? Много мелких insert без JOIN? Пик записи? | Кэш разгружает чтение; документная БД удобна для append-only |
| **Схема во времени** | Поля заказа меняются раз в квартал или у каждой записи свой набор атрибутов? | Миграции vs schemaless |
| **Объём и TTL** | Данные живут годы и обязаны переживать сбой диска? Часы (сессия)? Дни с ротацией (логи)? | Durability, eviction, TTL-индексы |
| **Операции** | Бэкапы, репликация, знакомый SQL, стоимость сопровождения | Учебный и промышленный контур SFMShop уже завязан на PostgreSQL |

Ниже три нагрузки проекта проходят через эти критерии — и получают разные СУБД.

## 2. Нагрузки SFMShop

| Нагрузка | Примеры в коде | Структура | Согласованность | Доступ |
|----------|----------------|-----------|-----------------|--------|
| **Основные данные** | `User`, `Product`, `Order`, `OrderItem` в `src/database/models.py`; `create_order`, `get_user_order_history` | Связанные таблицы, `Numeric` цены, уникальный email | Строгая: заказ без пользователя недопустим | JOIN, отчёты, транзакции |
| **Кэш и сессии** | `get_cached_products`, `create_user_session` в `src/services/cache_service.py` | Ключ → JSON, TTL 1 ч / 24 ч | Допустима устаревшая витрина; сессия не источник заказа | `GET`/`SETEX` по ключу |
| **Логи** | `save_log`, `get_logs_by_type`, агрегации в `src/services/log_service.py` | Полуструктурированный документ (`type`, `status_code`, произвольные поля) | Потеря одного лога хуже, чем рассинхрон заказа, но JOIN с заказами не нужен | Append + фильтры + `$group` |

Смешивать эти роли в одной БД можно технически, но критерии расходятся: ядро требует ACID и JOIN, витрина — миллисекундный ключ с TTL, логи — гибкую схему и поток вставок.

## 3. PostgreSQL — основные данные

**Выбор:** PostgreSQL как единственный **source of truth** для пользователей, каталога и заказов.

### Как критерии попадают в ядро магазина

- **Связи.** Один пользователь — много заказов; заказ — много позиций; позиция ссылается на товар. В схеме это `ForeignKey('users.id')`, `ForeignKey('orders.id')`, `ForeignKey('products.id')`. SQL JOIN собирает «заказ + товары + пользователь» без денормализации каталога в каждый заказ.
- **Целостность.** Уникальный `email`, денежный `Numeric(10, 2)`, транзакция на создание заказа. БД отклоняет заказ с несуществующим `user_id`. Остаток `products.quantity` при оформлении нельзя решать «примерно».
- **Запросы.** История (`get_user_order_history`), статистика (`get_order_statistics`), топ товаров (`get_top_products`), отчёты (`generate_sales_report`) — агрегаты и индексы (`user_id`, имя товара), а не обход всех документов.
- **Стабильная схема.** Поля заказа и товара меняются редко; миграции DDL версионируют контракт. Это плюс, не минус.
- **Долговечность.** Заказ и оплата должны пережить рестарт приложения и сбой кэша.

### Почему не MongoDB и не Redis на эту роль

| Альтернатива | Почему хуже для ядра SFMShop |
|--------------|------------------------------|
| MongoDB как основная БД заказов | Нет классических FK; целостность и «заказ без пользователя» уезжают в приложение. Сквозные отчёты — `$lookup` или дублирование каталога в каждом заказе. |
| Redis как хранилище заказов | Данные в RAM (persistence опциональна и слабее WAL PostgreSQL). Нет JOIN и денежных ограничений. TTL и eviction противоречат «заказ живёт годы». |

PostgreSQL уже используется так: запись на primary, чтение витрины и истории — с replica (`get_session(read_only=True)`). Репликация масштабирует чтение ядра; кэш и логи эту роль не подменяют.

## 4. Redis — кэш (и сессии)

**Выбор:** Redis как **не источник истины**, а слой поверх PostgreSQL: горячие ключи витрины и короткоживущие сессии.

### Как критерии попадают в кэш SFMShop

- **Структура — ключ–значение.** `products:all`, `product:{id}`, `session:{uuid}` — точечное чтение без JOIN.
- **Согласованность — ослабленная.** Витрина может отставать до TTL (в коде — 3600 с) или до `invalidate_products_cache()`. После смены цены товар в Redis может быть старым, пока ключ не истечёт или не удалят. Для карточки товара это приемлемо; для списания остатка — нет (остаток читается из PostgreSQL).
- **Нагрузка — много одинаковых GET.** Каталог читают чаще, чем меняют. Cache-aside в `get_cached_products()`: сначала Redis, при промахе — `get_all_products()` из PostgreSQL, затем `SETEX`.
- **TTL.** Сессия — `setex(..., 86400, ...)`; товар — час. Истечение ключа — штатный способ забыть данные, а не сбой.
- **Задержка.** Обращение по ключу в RAM дешевле SQL по `products` на каждый `GET /products`.

### Что именно кэшируется в проекте

| Ключ | Зачем | TTL |
|------|--------|-----|
| `products:all` | Список витрины | 1 час |
| `product:{id}` | Карточка товара | 1 час |
| `session:{id}` | Кто залогинен, без строки в `users` на каждый запрос | 24 часа |

Инвалидация (`invalidate_product_cache`) нужна после изменения цены или остатка на primary — иначе Redis будет врать дольше TTL.

### Почему не PostgreSQL и не MongoDB на эту роль

| Альтернатива | Почему хуже как кэш |
|--------------|---------------------|
| Материализованные таблицы / UNLOGGED в PostgreSQL | Нет естественного TTL и eviction; primary и так занят заказами. Кэш должен разгружать БД, а не жить в ней же. |
| MongoDB как кэш каталога | Лишняя постоянная коллекция, выше латентность, чем у in-memory KV; нет `SETEX` как основного API. |

Redis **не заменяет** PostgreSQL: после `FLUSHALL` или рестарта без AOF каталог восстанавливается из БД. Сессию при потере Redis пользователь просто логинится снова — заказ от этого не исчезает.

## 5. MongoDB — логи

**Выбор:** MongoDB (коллекция `sfmshop_logs.logs`) для событий доступа, ошибок и служебных записей — не для заказов.

### Как критерии попадают в логи SFMShop

- **Гибкая схема.** У access-лога есть `endpoint` и `status_code`, у error — `message` и иногда `stack`; у записи по IP — поле `ip`. Не нужно заранее описывать все колонки. `save_log` принимает словарь и при необходимости добавляет `timestamp`.
- **Слабая связь с ядром.** Логи не обязаны JOIN-иться с `orders` по FK. Потеря или задержка одной записи лога не ломает оформление заказа.
- **Append-only и объём.** Поток вставок (`insert_one`) велик относительно изменения схемы. Документная модель и шардирование по времени/полям здесь естественнее, чем бесконечно растущая таблица в той же БД, что и заказы.
- **Запросы — фильтры по полям, не JOIN.** `get_logs_by_type`, `get_logs_by_status_code` (`$gte` / `$lt`), `get_logs_by_ip`, `get_logs_by_date_range`, агрегация `$group` по `type` и `status_code`. Это поиск по документам, а не «заказ + позиции + пользователь».
- **Эволюция.** Завтра в лог можно добавить `user_agent` или `request_id` без миграции всех исторических строк.

В учебном контуре тот же паттерн показан коллекцией документов с фильтрами `$gte`, `$in` (урок логирования в `src/main.py`); промышленный путь — `pymongo` в `log_service.py`.

### Почему не PostgreSQL и не Redis на эту роль

| Альтернатива | Почему хуже для логов SFMShop |
|--------------|-------------------------------|
| Таблица логов в PostgreSQL рядом с заказами | Жёсткая схема или «простыня» JSONB; рост таблицы конкурирует с `VACUUM` и бэкапами заказов; разнородные события требуют частых ALTER или разреженных колонок. JSONB возможен, но тогда ядро и «свалка событий» делят один контур восстановления. |
| Redis (списки, Streams) | Удобно как буфер, плохо как долговременный архив с произвольными запросами по дням, IP и типам. RAM и eviction конфликтуют с «найти ошибки за неделю». |

MongoDB **не заменяет** PostgreSQL для `Order`: отсутствие жёстких FK как раз то, что *мешает* ядру и *помогает* логам.

## 6. Что получится, если перепутать роли

| Если сделать так | Следствие |
|------------------|-----------|
| Заказы в MongoDB, каталог «как получится» | Риск заказа без пользователя, дубли цен, сложные отчёты |
| Каталог только в Redis | После рестарта пустая витрина; нет денежных ограничений и истории |
| Логи в той же БД, что заказы, без отделения | Раздувание бэкапов ядра, шум в схеме, конкуренция I/O с `create_order` |
| Сессии в PostgreSQL на каждый клик | Лишняя запись на primary ради данных, которые должны истечь за сутки |

Разделение ролей снижает эти риски: сбой Redis не уничтожает заказы; сбой MongoDB не останавливает checkout; сбой PostgreSQL останавливает магазин — и это правильно, потому что там источник истины.

## 7. Сводка

| Роль | СУБД | Главные критерии | В коде SFMShop |
|------|------|------------------|----------------|
| Основные данные | **PostgreSQL** | Связи, ACID, JOIN, стабильная схема, долговечность | `models.py`, `queries.py`, primary/replica |
| Кэш и сессии | **Redis** | Ключ–значение, TTL, низкая задержка, допустимая устарелость | `cache_service.py`: витрина и `session:*` |
| Логи | **MongoDB** | Гибкий документ, append, фильтры без JOIN с заказами | `log_service.py`: `sfmshop_logs.logs` |

Критерий выбора — **соответствие модели данных и гарантий нагрузке**, а не универсальность одной СУБД. Для SFMShop это означает: PostgreSQL держит деньги и связи, Redis ускоряет повторные чтения, MongoDB принимает разнородный поток логов, не усложняя схему магазина.
