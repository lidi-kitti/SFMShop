# Стратегия масштабирования БД SFMShop

SFMShop хранит пользователей, каталог и заказы в PostgreSQL. Пока объём данных и нагрузка помещаются на один сервер, достаточно индексов и вертикального масштабирования (больше CPU/RAM/диска у primary). Когда один инстанс перестаёт справляться, появляются два разных инструмента: **репликация** и **шардирование**. Их нельзя подменять друг другом: они решают разные узкие места.

В коде уже заложена развилка «запись / чтение»:

- запись идёт на primary (`DB_PRIMARY_HOST`, порт `DB_PORT`);
- чтение может идти на replica (`DB_REPLICA_HOST`, порт `DB_REPLICA_PORT`);
- маршрутизация сессии — `get_session(read_only=...)` в `src/database/models.py` и `get_connection(read_only=...)` в `src/database/connection.py`.

Ниже — когда включать каждый механизм, как это выглядит для сущностей магазина и какие компромиссы принимать заранее.

---

## 1. Порядок решений

| Этап | Что происходит | Когда переходить дальше |
|------|----------------|-------------------------|
| Один primary | Все чтения и записи на одном PostgreSQL | Медленные SELECT по каталогу/заказам, рост CPU на чтении, но запись ещё умеренная |
| Репликация (primary + read replicas) | Запись на primary, чтение витрины и истории — с реплик | Реплики разгрузили чтение, но primary упирается в запись, диск или размер таблиц `orders` / `order_items` |
| Шардирование | Данные разрезаны по ключу (для SFMShop — `user_id`) на несколько независимых БД | Один primary уже не держит объём или write-нагрузку даже после реплик |

Правило: **сначала репликация, шардирование — только когда вертикаль и реплики исчерпаны.** Шарды меняют модель запросов (JOIN между шардами практически недоступен) и стоимость эксплуатации.

---

## 2. Репликация: когда применять

Репликация — это копии одной и той же базы. Primary принимает все `INSERT`/`UPDATE`/`DELETE`, реплики асинхронно (в типичной схеме PostgreSQL streaming replication) получают WAL и отдают `SELECT`.

### Когда это уместно для SFMShop

Репликацию включают, когда:

1. **Чтений намного больше, чем записей.** Типичный магазин: витрина и карточки товаров открываются постоянно, заказы создаются реже.
2. **Primary занят SELECT'ами**, а не записью: список товаров, история заказов, отчёты.
3. **Нужен запас на отказ primary** (реплика как кандидат в failover) — это бонус, не единственная цель масштабирования чтения.
4. **Данные ещё помещаются на один сервер.** Реплика копирует *весь* объём; она не уменьшает размер таблиц.

Репликация **не поможет**, если узкое место — запись остатков, пик оформления заказов или таблица `orders`, которая уже не влезает на диск одного узла.

### Что читать с реплики в SFMShop

В проекте чтение уже помечено `read_only=True` и должно идти на replica.

| Операция | Функция | Почему реплика |
|----------|---------|----------------|
| Список и карточка товара | `get_all_products()`, `get_product_by_id()` | Витрина — самый частый трафик; небольшая задержка реплики обычно приемлема |
| История заказов пользователя | `get_user_orders()`, `get_user_order_history()`, `get_orders_with_products()` | Личный кабинет: JOIN `orders` + `order_items` + `products` без нагрузки на primary |
| Статистика и отчёты | `get_order_statistics()`, `get_top_products()`, `generate_sales_report()`, `calculate_total_revenue()` | Тяжёлые агрегаты не должны конкурировать с `create_order` |

Пример маршрутизации (уже в коде):

```python
# запись — только primary
session = get_session(read_only=False)
create_order(user_id, total)

# каталог и история — replica
with get_connection(read_only=True) as conn:
    products = get_all_products(conn)

orders = get_user_orders(user_id)          # _session_scope(read_only=True)
history = get_user_order_history(user_id)  # то же
```

### Что нельзя отдавать реплике без оговорок

| Операция | Почему primary |
|----------|----------------|
| `create_order`, `create_user`, `add_product` | Реплика в PostgreSQL read-only |
| Списание `products.quantity` при оформлении заказа | Нужна актуальная строка и блокировка; лагающая реплика может показать «есть в наличии», которого уже нет |
| Подтверждение оплаты / смена статуса заказа сразу после записи | Клиент ожидает увидеть свой только что созданный заказ |

Практический паттерн: **read-your-writes** для текущего пользователя. После `POST /orders` следующий `GET` этого заказа идёт на primary (или приложение ждёт, пока replica догонит LSN). Остальной каталог по-прежнему читается с реплики.

## 3. Шардирование: когда применять

Шардирование — горизонтальный разрез данных: несколько независимых PostgreSQL, у каждого свой набор строк. Репликация копирует всё; шард хранит только свою долю.

### Когда это уместно для SFMShop

Шарды рассматривают, когда выполняется хотя бы одно:

1. **Таблица заказов не помещается на один сервер** (диск, RAM под индексы, время `VACUUM`/`ANALYZE`).
2. **Запись saturates primary** даже после выноса чтений на реплики: пики `create_order`, обновления остатков.
3. **Нужно изолировать нагрузку** по сегментам клиентов (регион, крупный B2B-аккаунт) — реже как первый шаг, чаще как следствие ключа шардирования.

Шардирование **не нужно**, пока помогает реплика плюс индексы (`idx_orders_user_id`, индекс по `products.name` и т.д.). Стоимость шардов выше реплик на порядок: роутинг в приложении, миграции схемы на каждый шард, кросс-шардные отчёты.

### Ключ шардирования: `user_id`

Для SFMShop естественный ключ — **`user_id`**. Заказ всегда принадлежит одному пользователю (`Order.user_id`). Если пользователя и его заказы класть на один шард, типичный JOIN остаётся локальным.

Это уже смоделировано в `ShardRouter` (`src/main.py`):

```text
shard = md5(user_id) % N
orders(user_id) → тот же шард, что и users(user_id)
```

| Сущность | Куда класть | Почему |
|----------|-------------|--------|
| `users` | шард от `user_id` | Владелец данных |
| `orders` | шард от `user_id` заказа | История и «мои заказы» без fan-out |
| `order_items` | шард заказа (= шард `user_id`) | Позиции едут вместе с заказом |
| `products` | **не шардировать по пользователю** | Каталог общий; либо отдельный маленький кластер/реплики каталога, либо копия справочника на каждом шарде |

Почему не шардировать заказы по `order_id` или `product_id`:

- по `order_id` запросы «все заказы пользователя» бьют по всем шардам;
- по `product_id` один заказ с несколькими товарами разъезжается по шардам, JOIN ломается.

### Что остаётся сложным даже с хорошим ключом

- **Глобальный каталог.** `get_all_products()` и остатки — общая таблица. Её либо держат на отдельном primary+replica (без шардов), либо реплицируют справочник на каждый шард и мирятся с расхождением цен/остатков.
- **Сквозные отчёты.** `get_top_products()`, `generate_sales_report()`, `get_order_statistics()` должны либо ходить во все шарды и сливать результат в приложении, либо писаться в отдельное аналитическое хранилище (реплика/OLAP), а не считаться online с шардов.
- **Уникальность email.** `users.email UNIQUE` на одном шарде не гарантирует уникальность во всём кластере — нужна глобальная проверка или выделенный сервис идентичности.
- **Ребалансировка.** Смена числа шардов ломает `md5(user_id) % N`. Для роста кластера нужен consistent hashing или таблица соответствия `user_id → shard`, иначе придётся переливать данные.

## 4. Компромиссы

Оба подхода дают пропускную способность ценой согласованности, задержки и сложности эксплуатации.

### 4.1. Задержка репликации (replication lag)

Реплика отстаёт от primary на миллисекунды… секунды (при нагрузке, сети, долгих транзакциях — минуты).

Для SFMShop это значит:

- пользователь оформил заказ на primary, сразу открыл «мои заказы» с реплики — заказа может не быть;
- админ изменил цену товара — витрина с реплики ещё показывает старую цену;
- отчёт `calculate_total_revenue` чуть занижает сумму за последний интервал.

Смягчение: критичные read-your-writes на primary; мониторинг лага (`pg_stat_replication`, `replay_lag`); не использовать сильно отстающую реплику для витрины.

### 4.2. Eventual consistency

Асинхронная реплика даёт ** eventual consistency**: рано или поздно реплика догонит primary, но в моменте разные узлы показывают разное.

Где в магазине это допустимо:

- каталог (`GET /products`) — допустима задержка в секунды;
- витрина топа продаж — допустима;
- история заказов «как витрина» — обычно допустима, кроме сразу после checkout.

Где недопустимо без доп. мер:

- остаток `products.quantity` при checkout (оверселл);
- идемпотентность оплаты;
- уникальность email при регистрации, если проверка шла только по реплике.

Шарды добавляют другой вид расхождения: нет одной транзакции на «пользователь на шарде A + списание товара на узле каталога». Оформление заказа становится распределённой операцией (saga / outbox), а не одним `COMMIT` на primary.

### 4.3. Сложность настройки и сопровождения

| | Репликация | Шардирование |
|---|------------|----------------|
| Настройка PostgreSQL | primary + `standby`, слоты репликации, user с правом репликации | N независимых кластеров, бэкапы, миграции схемы на каждый шард |
| Приложение | флаг `read_only`, два DSN (`DB_PRIMARY_*` / `DB_REPLICA_*`) | роутер (`ShardRouter`), знание ключа в каждом запросе |
| Отказы | failover primary → replica (Patroni и аналоги) | отказ шарда недоступен целому срезу пользователей |
| Запросы | те же SQL, что на одном сервере | запрет кросс-шард JOIN; отчёты — scatter-gather |
| Операции | один бэкап-контур на роль | N бэкапов, ребаланс, смена ключа почти невозможна |

Репликация в SFMShop уже близка к текущему коду: достаточно поднять replica и гонять `read_only=True` на неё. Шарды потребуют переписать доступ к `users`/`orders`/`order_items` через `shard_for_user`, вынести каталог и пересобрать отчёты.

Дополнительная сложность реплик: split-brain при неаккуратном failover, magically «исчезнувшие» записи при rewind, необходимость не писать в replica (приложение должно это гарантировать, а не только `default_transaction_read_only`).

---

## 5. Сводка для SFMShop

```text
Нагрузка на чтение каталога и истории
        │
        ▼
  Репликация: GET товаров и заказов → replica
              POST заказа, остатки, оплата → primary
        │
        ▼  (primary всё ещё не справляется по записи/объёму)
  Шардирование по user_id:
              users + orders + order_items на шарде пользователя
              products — общий сервис/кластер
              отчёты — отдельно, не online JOIN по всем шардам
```

**Репликация** масштабирует чтение и даёт копию для failover. Для SFMShop это чтение товаров и заказов с replica при записи на primary. Цена: лаг, eventual consistency, аккуратная маршрутизация сессий.

**Шардирование** масштабирует запись и объём. Для SFMShop ключ — `user_id`, чтобы пользователь и его заказы жили вместе. Цена: сложность роутинга, потеря простых глобальных JOIN, отдельная стратегия для каталога и отчётов.

Не включать шарды «на всякий случай»: пока каталог и заказы читаются с реплики, а primary справляется с `create_order`, текущая схема primary + replica — достаточная и более дешёвая стратегия.
