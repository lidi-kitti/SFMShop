# Сравнение веб-фреймворков для проекта SFMShop

SFMShop — учебный интернет-магазин с REST API: каталог, пользователи, заказы, сессии в Redis, фоновая обработка. Приложение уже живёт в `src/api/main.py` на **FastAPI**; доменные модели и SQLAlchemy не зависят от веб-слоя. Ниже FastAPI и Django сравниваются не «вообще», а по тому, что реально нужно магазину.

Критерии те же, что при выборе СУБД: соответствие нагрузке, а не универсальность фреймворка.

| Критерий | Вопрос для SFMShop |
|----------|-------------------|
| **Контракт API** | JSON-маршруты (`/products`, `/orders`, `/login`), OpenAPI, валидация тела запроса |
| **Асинхронность** | Параллельные запросы к БД (`GET /api/products/{id}/full`), Redis, `BackgroundTasks`, `asyncpg` |
| **Слой данных** | Уже есть SQLAlchemy + PostgreSQL, Redis, MongoDB — не Django ORM |
| **Админка и HTML** | Одна форма в `templates/admin.html`, витрина — клиент по JSON, не серверный рендер |
| **Учебный контур** | Явные модели OOP, сервисы, ручной SQL/ORM — «батарейки» не должны прятать устройство магазина |

---

## FastAPI

ASGI-фреймворк: маршруты — обычные функции, схемы — Pydantic, документация — из типов. В проекте это `uvicorn src.api.main:app`, `Depends`, `HTTPBearer`, lifespan с пулами `httpx` / Redis / `asyncpg`.

### Преимущества

- **API как основная поверхность.** `GET /products`, версии `/api/v1` и `/api/v2`, заголовки `Cache-Control` и `Authorization: Bearer` описываются прямо в хендлерах. Swagger (`/docs`) появляется без отдельного слоя вроде DRF.
- **Нативный async.** `GET /api/products/{id}/full` параллельно тянет товар, отзывы и счётчик просмотров; `POST /orders/process` ждёт `process_orders_async`; `POST /orders/process-background` отдаёт 200 и продолжает работу. Это тот же `asyncio`, что в `async_service.py` и `async_repository.py`.
- **Стек уже совпадает.** Pydantic в `requirements.txt`, SQLAlchemy 2, `asyncpg`, `redis.asyncio`. Не нужно переносить модели `User` / `Product` / `Order` в чужой ORM.
- **Тонкий слой над доменом.** Валидация, сессии Redis, кэш витрины остаются в сервисах. Фреймворк не диктует структуру таблиц и не смешивает HTML с заказом.
- **Скорость разработки REST.** Новый ресурс — функция + модель запроса/ответа. Для учебного магазина это короче, чем «проект Django → приложение → serializer → viewset».

### Недостатки

- **Нет «батареек» из коробки.** Админка, формы, пользователи, CSRF, шаблоны, миграции — собираются вручную. Сейчас админка — статический HTML; полноценная панель модерации каталога потребует своей реализации или отдельного UI.
- **Синхронный код рядом с async.** `get_session()` / psycopg2 в части маршрутов блокируют event loop, если вызывать их из `async def` без пула или threadpool. Дисциплина «где async, где sync» лежит на авторе, не на фреймворке.
- **Меньше готовых соглашений.** Нет единого «как устроен проект»: легко размазать логику между `main.py`, сервисами и SQL. Для большого монолита без договорённостей это минус.
- **Фоновые задачи ограничены процессом.** `BackgroundTasks` не очередь (Celery/RQ). После рестарта uvicorn незавершённая обработка заказов теряется — для учебного контура приемлемо, для продакшена нужен брокер.

### Когда использовать

- Основной продукт — **JSON API** (витрина, мобильный клиент, чужой фронтенд), а не сайт из шаблонов Django.
- Нужны **параллельный I/O** и долгие операции без блокировки ответа (обогащение карточки товара, пакетная обработка заказов, кэш Redis).
- Схема данных и ORM **уже выбраны** (SQLAlchemy + PostgreSQL) и не должны переезжать в Django.
- Команда хочет явный контракт (Pydantic + OpenAPI) и короткий путь от хендлера до сервиса.

## Django

MTV-фреймворк «всё включено»: ORM, админка, auth, шаблоны, миграции, middleware. API обычно добавляют через **Django REST Framework** или **Django Ninja**; async-views есть, но ORM и экосистема долго оставались синхронными.

### Преимущества

- **Админка и CRUD «из коробки».** Регистрация `Product` / `Order` в `admin.py` даёт модерацию каталога без самописного HTML. Для оператора магазина это быстрее, чем `templates/admin.html`.
- **Единый контур пользователей.** `django.contrib.auth`, сессии, CSRF, permissions — готовая модель «кто может POST /products». Сейчас в SFMShop сессия — UUID в Redis и ручной `require_auth`.
- **Миграции и ORM как стандарт.** `makemigrations` версионирует схему рядом с моделями; админка, формы и queryset живут в одном стиле. Удобно, если веб-слой и таблицы рождаются вместе.
- **Серверный HTML.** Если витрина — страницы Jinja/Django Templates, корзина и checkout без SPA, Django закрывает маршруты, формы и i18n одним стеком.
- **Зрелая экосистема магазина.** Плагины оплаты, CMS, «батарейки» для типичного монолита. Для классического сайта-магазина это плюс.

### Недостатки

- **Лишний вес для текущего SFMShop.** Проект — REST + кастомные модели + SQLAlchemy + Redis/Mongo. Django тянет свой ORM, свой user, свой project layout. Перенос — это не «подменить FastAPI», а **переписать слой данных и auth**.
- **API — второй гражданин.** JSON появляется через DRF/Ninja: serializers, viewsets, отдельная схема. OpenAPI не является центром фреймворка, в отличие от FastAPI.
- **Async слабее подходит к текущему коду.** Параллельный `asyncpg` в `get_product_full`, `redis.asyncio`, `httpx.AsyncClient` в lifespan — родная модель FastAPI. В Django до недавнего времени ORM в async-view часто уводили в sync или в обходки; фоновые задачи всё равно выносят в Celery.
- **Скрывает учебные слои.** Цель репозитория — явные классы домена, сервисы, ручные запросы. Django Admin и Generic views прячут этот контур за соглашениями фреймворка.
- **Синхронный WSGI по умолчанию.** Типичный деплой (gunicorn + sync workers) плохо сочетается с уроками про event loop, producer/consumer и неблокирующий I/O, которые уже лежат в `src/services/`.

### Когда использовать

- Нужен **полноценный бэк-офис** и серверные страницы, а API — приложение к сайту, не наоборот.
- Команда готова вести **модели только в Django ORM** и не держать параллельно SQLAlchemy.
- Приоритет — auth, формы, CSRF, админка, а не параллельные запросы к PostgreSQL и Redis.
- Проект ближе к классическому монолиту (каталог + статьи + кабинет), чем к отдельному REST-сервису витрины.

## Рекомендация для SFMShop

**Оставить FastAPI** как веб-слой. Он уже совпадает с формой проекта: JSON-API, Pydantic, async-обработка заказов, Redis-сессии, SQLAlchemy/asyncpg, тонкая админка.

Django был бы оправдан при смене продукта: серверная витрина, штатная админка модераторов, отказ от отдельного ORM. Для текущего контура это замена ядра ради функций, которые магазин либо не использует, либо закрывает точечно (HTML-форма, Bearer + Redis).

Если позже понадобится богатый бэк-офис, разумнее не переписывать API на Django, а добавить отдельный UI (или тонкий Django/Admin только для операций) поверх тех же таблиц PostgreSQL — источник истины остаётся в БД, а не во фреймворке.
