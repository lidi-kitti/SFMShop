# PostgreSQL и MongoDB для SFMShop: анализ и сравнение

## 1. Контекст проекта SFMShop

SFMShop — интернет-магазин с сущностями **пользователь** (`User`), **заказ** (`Order`), **товар** (`Product`). В коде уже заложены связи: заказ ссылается на пользователя и список товаров; товары участвуют в расчёте суммы заказа. Для полноценного хранения этих данных на сервере типичный выбор — реляционная СУБД, в частности **PostgreSQL**.

Ниже — требования к данным магазина и то, как им соответствуют PostgreSQL и MongoDB.

---

## 2. Требования к данным SFMShop

| Требование | Суть для магазина |
|------------|-------------------|
| **Связи** | Один пользователь — много заказов; заказ — много позиций (товар + количество + цена на момент заказа); товар — общий каталог. Нужны предсказуемые отношения «многие к одному» и «многие ко многим» (заказ ↔ товар через позицию заказа). |
| **Целостность** | Нельзя сохранить заказ без существующего пользователя; нельзя добавить в заказ несуществующий товар (или нужна явная политика «мягкого» удаления). Важны уникальность email, неотрицательные цены и остатки, согласованность суммы заказа с позициями. |
| **Сложные запросы** | Список заказов пользователя с товарами и суммами; отчёты по продажам; фильтры по датам, статусам, категориям; пагинация и сортировка. |
| **Стабильная схема** | Поля пользователя, заказа, товара и позиции заказа меняются редко; домен хорошо укладывается в таблицы и ограничения. |

---

## 3. Сравнение по задачам проекта

### 3.1. Связи между пользователями, заказами и товарами

- **PostgreSQL.** Связи выражаются внешними ключами (`user_id` в заказе, таблица позиций заказа с `order_id` и `product_id`). Модель читается из схемы БД; JOIN — естественный способ собрать заказ с пользователем и строками.
- **MongoDB.** Связи эмулируются вложенными документами или ссылками (`ObjectId`). Без дисциплины в приложении легко получить «висячие» ссылки; встроенные `$lookup` дают аналог JOIN, но без жёстких FK на уровне БД (в классической модели MongoDB).

**Для SFMShop лучше:** PostgreSQL — явная реляционная модель совпадает с предметной областью магазина.

---

### 3.2. Целостность данных

- **PostgreSQL.** `FOREIGN KEY`, `NOT NULL`, `UNIQUE`, `CHECK`, транзакции ACID. БД отклонит заказ с несуществующим `user_id` или нарушением бизнес-правил, если правила отражены в ограничениях.
- **MongoDB.** С версии 4.2+ есть схема валидации и транзакции в кластере, но «нельзя сослаться на несуществующий документ» как в FK — не встроено; ответственность частично на приложении.

**Для SFMShop лучше:** PostgreSQL — критична согласованность заказов с пользователями и каталогом.

---

### 3.3. Сложные запросы (заказы пользователя с товарами)

- **PostgreSQL.** Один или несколько SQL-запросов с `JOIN`, подзапросами, агрегатами, индексами по `user_id`, дате заказа, статусу. Оптимизатор и индексы B-tree / частичные индексы хорошо подходят для отчётов.
- **MongoDB.** Агрегационный pipeline (`$match`, `$lookup`, `$group`) справляется, но проектирование под частые запросы важно с первого дня; денормализация ускоряет чтение, но усложняет обновления и риски рассинхрона.

**Для SFMShop лучше:** PostgreSQL — типичные отчёты и «заказ + строки + пользователь» — стандартный реляционный сценарий.

---

### 3.4. Чёткая, редко меняющаяся структура

- **PostgreSQL.** Миграции (DDL) явно версионируют схему; типы колонок и ограничения документируют контракт данных.
- **MongoDB.** Гибкая схема удобна при частых изменениях формата, но для стабильного каталога и заказов даёт меньше гарантий «на диске» без дополнительной дисциплины (JSON Schema, валидация в приложении).

**Для SFMShop лучше:** PostgreSQL — домен магазина стабилен относительно потока заказов.

---

## 4. Почему для SFMShop выбирают PostgreSQL

1. **Модель данных** — классическая сеть сущностей с отношениями и числовыми инвариантами (цены, остатки, суммы).
2. **Целостность на уровне БД** — меньше классов ошибок при сбоях приложения или гонках при оформлении заказа.
3. **Запросы и отчёты** — SQL и индексы закрывают типичные сценарии без обязательной денормализации.
4. **Экосистема** — ORM, миграции, BI-инструменты, репликация, резервное копирование для учебных и промышленных проектов хорошо документированы.

Итог: для ядра магазина (пользователи, заказы, товары, оплаты) PostgreSQL **снижает риск неконсистентных данных** и **упрощает сложные выборки** по сравнению с типичным использованием MongoDB без дублирования схемы реляционной модели в документах.

---

## 5. Когда MongoDB был бы предпочтительнее

| Сценарий | Почему MongoDB |
|----------|----------------|
| **Логи приложения** | Большой объём полуструктурированных записей (уровень, сообщение, `stack trace`, произвольные поля контекста); горизонтальное шардирование по времени; слабая потребность в JOIN между логами и заказами. |
| **Неструктурированные или сильно меняющиеся данные** | Контент-страницы с произвольным JSON, черновики, интеграции с внешними API, где поля наборов различаются по поставщикам. |
| **Запись «в лоб» без жёсткой связи** | События аналитики, черновики корзины с экспериментальной структурой, если целостность с каталогом не критична на уровне документа. |
| **Документ как единица чтения** | Если основной доступ — «один документ = один заказ со всем внутри» и редкие сквозные отчёты по всем пользователям — MongoDB может быть удобна после продуманной денормализации (с компромиссами при изменении товара в каталоге задним числом). |

Важно: это не запрет использовать MongoDB для магазина — её **можно** спроектировать под заказы (вложенные позиции, денормализация), но **стоимость** поддержки целостности и отчётов обычно выше, чем у реляционной схемы на PostgreSQL для того же домена.

## 6. Краткая таблица плюсов и минусов

### PostgreSQL (для SFMShop как основное хранилище заказов и каталога)

| Плюсы | Минусы |
|-------|--------|
| FK, ограничения, транзакции | Горизонтальное шардирование сложнее, чем у типичного sharded MongoDB-кластера (для очень больших объёмов нужен отдельный дизайн) |
| Сложные JOIN и SQL-отчёты | Схема требует миграций при изменении модели |
| Предсказуемая модель для команды | — |

### MongoDB (в роли основной БД того же ядра магазина)

| Плюсы | Минусы |
|-------|--------|
| Гибкая схема документа | Нет классических FK; целостность чаще в приложении |
| Удобно писать большие потоки однотипных документов | Сложные сквозные отчёты и «все заказы с товарами» — либо pipeline, либо денормализация |
| Масштабирование чтения/записи документов в подходящих паттернах | Риск дублирования и рассинхрона при денормализации каталога в заказах |

---

## 7. Вывод

Для **SFMShop** с требованиями связей, целостности, сложных выборок и стабильной структуры **PostgreSQL** — естественный и практичный выбор для **основного** хранилища пользователей, заказов и товаров. **MongoDB** логичнее рассматривать для **вспомогательных** нагрузок того же продукта: логи, события, произвольные JSON-поля интеграций — там её сильные стороны раскрываются с меньшими компромиссами, чем при замене реляционного ядра магазина.
